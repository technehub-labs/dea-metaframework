# DEA Entity Storage Layout

**Version**: 1.1.0
**Date**: 2026-11-10
**Status**: Ratified
**Owner**: Emmanuel A. Otchere
**Scope**: Org-wide. All `dea-catalog-*` repos.

---

## 1. Purpose

Every DEA catalog repo stores canonical records in a filesystem layout that is human-walkable, machine-derivable, and permanently under the GitHub 1,000-entry directory listing limit. This document defines the layout convention, the README-per-folder rule, and the path-derivation contract.

## 2. ECF-coordinated repos with a decomposition hierarchy (business-processes)

### 2.1 Containment tree

```
entities/v1-alpha/
  <pc-slug>/                              49 PC folders (one per ECF cell)
    README.md                             cell-level prose: coordinate, domain/stage semantics, children
    <record>.yaml                         PC record
    <pg-slug>/
      README.md                           PG-level prose: record summary, children
      <record>.yaml                       PG record
      <bp-slug>/
        README.md                         BP-level prose: record summary, children
        <record>.yaml                     BP record
        <activity-slug>/
          README.md                       Activity-level prose: record summary, children
          <record>.yaml                   Activity record
          <task-slug>/                    5 per Activity
            README.md                     Task-level prose
            <record>.yaml                 Task record
```

The tree IS the decomposition hierarchy. Containment on disk = `composes[]` in the records. Path derivable from id (colons normalized to hyphens, `dea-catalog-` prefix dropped, lowercased).

### 2.2 Folder naming

As landed in `dea-catalog-business-processes` (current canonical form, post **CR-BP-117c** PR #159, the "Folder/Path Clarity: C-1 dir rename + C-3 path scheme" slice):

- **PC folder** (49, one per ECF cell): `<domain>-<stage>/`. The level token is not repeated in the directory name and the hash suffix is dropped. Example: `processes:pc-ao-activate-kusw2u` lands at `entities/v1-alpha/ao-activate/`.
- **PG / BP / Activity / Task folders** (deeper levels): human-readable record names (CamelCase variants of each record's `name:` field), per the C-1 dir rename. Example chain: `entities/v1-alpha/ao-activate/Licensed-Workforce-Mobilization/Mobilize-Licensed-Workforce/Activate-Signing-Authority-Or-Controlled-Function-Designation/`.
- **Record file** (the leaf): the full id normalized, colons to hyphens, lowercased. Example: `processes-pc-ao-activate-kusw2u.yaml`.

### 2.3 README-per-folder rule

Every folder at every level carries a `README.md` that states: the level, the record id, the coordinate, a prose summary from the record's own `definition`, and the enumerated children. READMEs are generated by the migration script and enriched by the documentation pipeline (EXT-04).

### 2.4 Wave-1 folder-naming form (superseded)

Before CR-BP-117c (PR #159), every directory carried slug+hash and the record file was named after the record rather than the full id. That form landed in `dea-catalog-business-processes` (Wave 1, PR #149) and was the canonical example before this section was updated. It is retained here for readers reconciling pre-migration artifacts:

```
processes:pc-pr-operate-fz2h3             -> entities/v1-alpha/pr-operate/
processes:group-pr-build-3d2h9            -> entities/v1-alpha/pr-build/pr-build-3d2h9/
processes:process-ge-retire-7a4kq         -> entities/v1-alpha/ge-retire/ge-retire-3d2h9/ge-retire-7a4kq/
processes:activity-pr-activate-8m2np7     -> entities/v1-alpha/pr-activate/pr-activate-3d2h9/pr-activate-7a4kq/pr-activate-8m2np7/
processes:task-fa-activate-confirm-2x9y4p -> entities/v1-alpha/fa-activate/fa-activate-3d2h9/fa-activate-7a4kq/fa-activate-8m2np7/fa-activate-confirm-2x9y4p/
```

The migration script (`scripts/migrate_to_v3_layout.py`, in `dea-catalog-business-processes`) rewrote every catalog repo from this form to the §2.2 form. The old-to-new id map is `reconciliation/migration-id-map.yaml` in each catalog repo.

## 3. Flat-layout repos (capabilities, actors, orgunits, objects, services, stakeholders)

Applies to business-capabilities as well: its catalog is single-level (no decomposition hierarchy), and ECF coordinates live as record fields (`ecf.primary` / `ecf.secondary`), not in the id or the path.

### 3.1 Flat entity tree

```
entities/v1-alpha/
  <entity-slug>-<hash>/                   one per record; slug = id minus
    README.md                             the `<namespace>:<level>-` prefix
    <record>.yaml                         (record file = full id, colons as hyphens)
```

- Flat containment (no L0-L4 tree). Worst-case directory: one per record.
- README.md per dir, same rule as ECF repos.
- Example: `capabilities:capability-asset-management-7a4kqz` -> `entities/v1-alpha/asset-management-7a4kqz/capabilities-capability-asset-management-7a4kqz.yaml`

## 4. GitHub 1,000-entry limit

GitHub truncates a directory listing at 1,000 entries (files and subdirectories alike; the contents API truncates the same way). Since 1.1.0 the rule is enforced, not prose:

- **Shard trigger: 800 entries.** Before any directory approaches 800 entries, a shard level is introduced (e.g. by first letter of slug) without changing the id system, so the §5 contract keeps holding. 800 leaves 200 entries of headroom to the truncation, so the remediation PR lands while the directory is still fully listable.
- **PR-time enforcement**: CST-017 of the cross-repo conformance suite (`tools/conformance_test_catalog_structure.py`, added by CR-CATALOG-STRUCT-11) fails any directory at or over 800 **tracked** entries, census over the whole repo (untracked local noise such as a `.venv` never counts).
- **Org-wide weekly enforcement**: rule R5 of the portfolio reconciler (`dea-governance/registers/reconcile_portfolio.py`) audits every registered repo from the git-trees API: WARN (watch, non-failing) at 500+ entries, FAIL at 800+.
- **Remedy**: the CR-MET-024 recipe: shard `entities/v1-alpha/<letter>/…` on the first character of the record slug (`0-9` fallback), record ids byte-identical, all tooling moved to recursive walking in the same change. Reference implementation: `dea-catalog-metrics` (`scripts/migrate_to_shard_layout.py`, `scripts/_catalog.py::shard_for_id`, `tests/test_layout.py`).

ECF-coordinated repos (containment tree) keep their worst case at ~15 entries per directory: permanently under the trigger. The live failure mode is an unsharded *flat concern* elsewhere in a repo (e.g. `change-requests/` or a contribution intake queue), which is why CST-017 and R5 census every directory, not just `entities/`.

## 5. Path-integrity contract

Every record's filesystem path must be derivable from its id. The CI gate `check_id_system.py` enforces this: given a record's id, the gate computes the expected path and asserts the record file exists at that path. No orphan files, no orphan records.
