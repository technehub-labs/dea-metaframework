# DEA Entity Storage Layout

**Version**: 1.0.0
**Date**: 2026-09-20
**Status**: Ratified
**Owner**: Coder (for eaojnr)
**Scope**: Org-wide. All `dea-catalog-*` repos.

---

## 1. Purpose

Every DEA catalog repo stores canonical records in a filesystem layout that is human-walkable, machine-derivable, and permanently under the GitHub 1,000-entry directory listing limit. This document defines the layout convention, the README-per-folder rule, and the path-derivation contract.

## 2. ECF-coordinated repos with a decomposition hierarchy (business-processes)

### 2.1 Containment tree

```
entities/v1-alpha/
  <pc-slug>/                              49 PC folders (one per ECF cell)
    README.md                             cell-level prose: coordinate, domain/stage semantics, children
    <record>.yaml                         PC record
    <pg-slug>/
      README.md                           PG-level prose: record summary, children
      <record>.yaml                       PG record
      <bp-slug>/
        README.md                         BP-level prose: record summary, children
        <record>.yaml                     BP record
        <activity-slug>/
          README.md                       Activity-level prose: record summary, children
          <record>.yaml                   Activity record
          <task-slug>/                    5 per Activity
            README.md                     Task-level prose
            <record>.yaml                 Task record
```

The tree IS the decomposition hierarchy. Containment on disk = `composes[]` in the records. Path derivable from id (colons normalized to hyphens, `dea-catalog-` prefix dropped, lowercased).

### 2.2 Folder naming

Folder names are the id minus the `<namespace>:<level>-` prefix (slug + hash suffix); the level token is not repeated in the directory name. As landed in dea-catalog-business-processes (Wave 1, PR #149):

```
processes:pc-pr-operate-fz2h3          -> entities/v1-alpha/pr-operate/
processes:group-pr-build-3d2h9         -> entities/v1-alpha/pr-build/pr-build-3d2h9/
processes:process-ge-retire-7a4kq      -> entities/v1-alpha/ge-retire/ge-retire-3d2h9/ge-retire-7a4kq/
processes:activity-pr-activate-8m2np7  -> entities/v1-alpha/pr-activate/pr-activate-3d2h9/pr-activate-7a4kq/pr-activate-8m2np7/
processes:task-fa-activate-confirm-2x9y4p -> entities/v1-alpha/fa-activate/fa-activate-3d2h9/fa-activate-7a4kq/fa-activate-8m2np7/fa-activate-confirm-2x9y4p/
```

### 2.3 README-per-folder rule

Every folder at every level carries a `README.md` that states: the level, the record id, the coordinate, a prose summary from the record's own `definition`, and the enumerated children. READMEs are generated by the migration script and enriched by the documentation pipeline (EXT-04).

## 3. Flat-layout repos (capabilities, actors, orgunits, objects, services, stakeholders)

Applies to business-capabilities as well: its catalog is single-level (no decomposition hierarchy), and ECF coordinates live as record fields (`ecf.primary` / `ecf.secondary`), not in the id or the path.

### 3.1 Flat entity tree

```
entities/v1-alpha/
  <entity-slug>-<hash>/                   one per record; slug = id minus
    README.md                             the `<namespace>:<level>-` prefix
    <record>.yaml                         (record file = full id, colons as hyphens)
```

- Flat containment (no L0-L4 tree). Worst-case directory: one per record.
- README.md per dir, same rule as ECF repos.
- Example: `capabilities:capability-asset-management-7a4kqz` -> `entities/v1-alpha/asset-management-7a4kqz/capabilities-capability-asset-management-7a4kqz.yaml`

## 4. GitHub 1,000-entry limit

- ECF-coordinated repos: worst-case directory is ~15 entries (BP with the most Activities). Permanently under the limit.
- Non-ECF repos: worst-case directory is the number of records (currently 32 for capabilities, 18 for services). If any repo approaches 800 records, a shard level is introduced (e.g. by first letter of slug) without changing the id system.

## 5. Path-integrity contract

Every record's filesystem path must be derivable from its id. The CI gate `check_id_system.py` enforces this: given a record's id, the gate computes the expected path and asserts the record file exists at that path. No orphan files, no orphan records.
